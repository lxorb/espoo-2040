# Experiments

Every number in the paper is a macro in `paper/figs/numbers.tex` or a row in a `paper/figs/*.tex` table. All of them are written by `paper/figs/make.py`, run through `paper/build.sh`. This file says where each one comes from.

Score: `(D_nothing - D) / (D_nothing - D_best)` with `sim/norms.json` (frozen at commit `d24719a`), clipped to [0, 1] unless a row says raw. Saved share: `1 - D / D_nothing` on the same seed. Delay `D`: total person-hours over 2026 to 2045.

## Rebuild

`paper/build.sh` needs only committed files: `sim/norms.json`, `data/catalogue.json`, `evidence/`, and the summaries in `paper/figs/data/`:

| File | Content | Made by |
|---|---|---|
| `runs.json` | per-seed delays, spend, builds, maintenance of all simulated and Harbor runs | `collect.py` from scratch run folders and `jobs/` |
| `rl.json` | RL strategy rows (up to `CUT` = 5280 episodes for PPO from scratch), PPO and Gumbel curves, search, `jam` ablation, unseen-seed results | `collect.py` from `runs/rl/` |
| `grpo.json` | GRPO evaluation per step (greedy plan and saving per seed) and run A strategy rows | `collect.py` from `runs/grpo/` |
| `growth.json`, `booms.json` | seed 1 area growth; growing areas of seeds 0 to 15 | `prep.py` |

When `runs/` and `jobs/` exist, `build.sh` first runs `collect.py` to refresh these summaries. Tested on a fresh `git clone` (with the pending changes to `paper/figs/` and `paper/build.sh` copied in): the build gives the same `numbers.tex`, tables and figures as the working copy, and 10 pages.

## Data split

| Split | Seeds | Use |
|---|---|---|
| train | 1000+ (BC, GRPO), 2000+ (PPO) | training only |
| validation | 0 to 15 | checkpoint choice, all headline scores |
| test | 16 to 47 | never used for training or selection |

The learned policy checkpoint was chosen on validation seeds 0 to 15 (highest mean plus worst score). Every validation number for it is therefore optimistic; the test split measures by how much (`hoGap`).

## Conflicts

Claims in README or paper that the evidence contradicts or qualifies, and open questions.

1. The main table now comes from `evidence/test.json` (Intel, frozen norms) and the a1 agent runs. Older macros from the AMD scratch runs (`rlScore`, `reactiveMTwo`, `greedyFiveMTwo` and similar) are kept only for the old text; across CPU types scores can differ by up to 0.008.
2. Learned policy, forecast check and rule planner numbers come from scratch `drive.py`, and maintenance-forced baselines from scratch `bl2.py`. Neither script is in the repository. `rl/eval.py` now covers the same policies (`deploy`, `planner`, `reactive:2`, ...) but not `rlcheck`.
3. PPO from scratch kept training after the paper text was written. `collect.py` freezes its strategy rows and its curve at 5280 episodes (`CUT`), which gives the values the text was written with (`evoColdEps` 5280, `evoColdScore` 0.71). The live file now reaches 20640 episodes with score 0.65; commit fff88a6 holds those live values in `numbers.tex`.
4. `curves.pdf` (a) and the Gumbel numbers come from stored runs; the Gumbel training path is no longer in the code.
5. The raw run files (`runs/`, `jobs/`, `viz/data/`) are gitignored. Their small summaries are committed in `paper/figs/data/` (see Rebuild), so the figures rebuild from a fresh clone, but the summaries themselves can only be regenerated on a machine that has the raw files.
6. README said the agent lacks cash for a 120 MEUR upgrade because it buys cheap links first and keeps maintenance at level 2 ("the reference plan with maintenance 2 scores 0.52 on seed 0"). The replays do not support this: the agent with maintenance 1 loses on all five seeds (`cfMaintOneDiff`), a growing-area upgrade is unaffordable in about as many years for the agent as for the reference (`failBlockedAgent`, `failBlockedRef`), and level 2 is only `failMaintTwoShare` of the agent's spend. Forcing maintenance 2 on the reference does cost it `cfRefMaintTwoDiff`, but the effect is not symmetric. Adding one access upgrade closes only `cfAccessGapShare` of the gap, so the gap comes from the whole plan, not one choice. README is corrected.
7. The README score table used AMD numbers. On Intel the reference minus agent gaps on seeds 0 to 4 are 0.482, 0.397, 0.032, 0.056, 0.058 (mean `gapIntelMean`, 95% CI [`gapIntelLo`, `gapIntelHi`], reference wins `gapIntelWins`, sign p `gapIntelSignP`); README now shows the Intel scores from `evidence/failures.json`.
8. Exploit suite on all 16 seeds (`exploits.tex`). The reference plan is complete after year `ExploitPlanDoneYear` and its cash first turns negative in year `ExploitFirstNegative` on every seed; after that every new action is rejected, so stopping after 7 or more years gives exactly the full score (`ExploitStopSevenGap`). Debt has no floor because emergency rebuilds are always paid (mean end cash `ExploitRefDebt` MEUR; do nothing reaches debt in year `ExploitNothingFirstNegative`, end cash `ExploitNothingDebt`). The reference with maintenance 0 beats it on `ExploitMaintZeroWins` of `ExploitMaintZeroN` seeds (sign p `ExploitMaintZeroP`) but is lower on average (`ExploitMaintZeroGap`) because of a few large losses; the reference always chooses maintenance 1. No malformed input was accepted (`ExploitRejected`). Whether the rules change is the owner's decision; README and paper conclusions are unchanged.
9. The reference checkpoint was chosen on 2026-11-14 18:26, when PPO had reached 560 episodes. A later checkpoint (800 episodes) is slightly better by the same rule (1.8482 against 1.8455), so "best" means best at that time.
10. The older `runs/rl/heldout.json` already evaluated seeds 16 to 47 after the fact. Its numbers agree with `evidence/test.json` (`hoRl` = `testRl`); it serves only as a cross-check.
11. Earlier reports gave reactive 0.566 and 5-year greedy 0.281 (old norms, maintenance 1). `evidence/test.json` was regenerated: maintenance-forced greedy now also uses that level inside its forecasts (as the old scratch script did), and `rlcheck` was added. Validation scores are now reactive with maintenance 2 `valReactiveScore`, 5-year greedy with maintenance 2 `valGreedyFiveScore` (was 0.475), 1-year greedy with maintenance 2 `valGreedyOneScore` (was 0.352; maintenance 1 is now better, `valGreedyOneMOneScore`), forecast check `valRlcheckScore`. On the test split 5-year greedy with maintenance 2 is `testGreedyFiveScore` (was 0.409) and 1-year greedy `testGreedyOneScore` (was 0.365). README's reactive 0.56 still holds.
12. PPO from scratch stopped at 20960 episodes; its last eight checkpoints score 0.65 to 0.76. `CUT` = 5280 stays, because the paper text was written with those values.
13. Norms. `D_nothing` is do nothing with maintenance 1. For seeds 16 to 47, `tools/norms.py` takes `D_best` as the minimum over: single-project orderings by full-run gain (6 truncations) with maintenance 1 and 2; random, greedy, 5-year greedy and reactive with maintenance 1 and 2; the current rule planner (late off and on); the current learned policy; then three rounds of local search from the best plan (rng [1, seed]). It cannot reproduce the frozen `D_best` of seeds 0 to 15 bit for bit: their pool held the deleted first planner, old deploy logs and a different random order. Recomputed for seeds 0 to 2, `D_nothing` is bit-identical, but `D_best` is 82045981 against frozen 82361722 (seed 0), 82005639 against 83619418 (seed 1) and 71955528 against 70937440 (seed 2). So the new procedure is stronger on seeds 0 and 1 and slightly weaker on seed 2, and test norms are mostly stricter than validation norms (on seed 1 the same plan scores about 2.8% lower). Validation and test scores must not be compared directly; this belongs in the paper's limitations. Because the learned policy and the rule planner are candidates for the test `D_best`, their test scores are at most 1. For seeds 2, 7 and 13 the frozen `D_best` was back-computed from a 3-decimal score; replaying that plan gives a true loss higher by 5605, 6507 and 2228 person-hours.

14. Random valid plans now score `grpoRandomVal` (8 per seed, the first 2 to 6 projects of a random permutation, maintenance drawn from 0, 1, 2: the target distribution of the format warm-up). An older paper draft quoted "random list 0.393/0.433", which used 6 projects and fixed maintenance 1 or 2.
15. The final GRPO model equals one constant plan on all `grpoSameAsConst` of 48 seeds, and its plans do not change when the growth numbers in the prompt are shuffled or zeroed (`grpoSensFinalShuffle`, `grpoSensFinalZero`; after warm-up `grpoSensWarmShuffle`, `grpoSensWarmZero`). It does not read growth.
